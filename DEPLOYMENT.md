# Dombi Riders — ръководство за реален деплой

Този документ описва какво е готово, какво остава, и точните стъпки за да
качите системата в реална (публично достъпна) среда.

## 0. Текущо състояние (накратко)

- Пълноценно работещо Node.js приложение (`server.js`, чист HTTP сървър без
  тежки зависимости) + статичен фронтенд (`public/`).
- **База данни:** избран е **Free план в Render**, който няма постоянен
  диск — затова `lib/db.js` вече поддържа Postgres (Supabase) като истински
  постоянен склад: цялата база се пази като един JSON ред в таблица
  `kv_store`, зареден в паметта при старт и записван асинхронно при всяка
  промяна (виж коментара в началото на `initDb()`/`readDb()`/`writeDb()` в
  `lib/db.js`). Пълната релационна схема (`schema.sql`) остава подготвена
  за бъдеща по-мащабна миграция (т. 4) — kv_store подходът е нарочно
  минимална, безопасна междинна стъпка, която НЕ изисква пренаписване на
  останалата логика на приложението.
  - Supabase проектът вече е свързан и таблицата `kv_store` е създадена
    (миграция `create_kv_store`, с RLS "deny all" по подразбиране — вижда
    се само през директна Postgres връзка, никога през публичния ключ).
  - При първо реално стартиране в Render (с зададен `DATABASE_URL`)
    сървърът сам засява `kv_store` от бандлнатия `data/db.json` (реалните
    данни от бекфила) — не се налага ръчен SQL импорт.
- **Реални данни вътре:** `data/db.json` (и след първия деплой — `kv_store`
  в Supabase) вече съдържа реалната история на заработките от Bolt Food и
  Glovo (Freestreets BG/DOMBI) — 70 профила на шофьори и 317 седмични
  записа (15 седмици Glovo + 1 седмица Bolt). Виж т. 5 "Бележки по реалните
  данни" за важни детайли и ограничения.
- **Сигурност:** пароли с scrypt хеш, rate limiting на login/apply
  маршрутите, HttpOnly+SameSite (+Secure в продукция) бисквитки, валидация
  на качени файлове, маскирано ЕГН в интерфейса. Виж секция "Сигурност и
  лични данни" в `README.md` за пълен списък и оставащи препоръки.
- **Мобилен изглед:** вътрешната система (`public/*.html` + `css/app.css`)
  и маркетинг сайтът (`../dombi-riders/index.html`) са тествани и оправени
  за мобилни устройства (странично меню, overflow фиксове).
- **Импорт на бъдещи седмици:** `public/payroll.html` вече има панел за
  качване на .xlsx файл от Bolt/Glovo с преглед преди запис — виж т. 6.

### Единствената останала пречка: Git repo

Render винаги деплойва от Git хранилище (GitHub/GitLab) — не приема директно
качен .zip файл, а Claude няма свързан GitHub connector, за да ти го
инициализира сам. Имаш два варианта:

**А) Свържи GitHub към claude.ai** (Настройки → Connectors) — тогава мога
   сам да създам repo-то, да кача кода и да довърша целия Render деплой.

**Б) Качи кода в GitHub сам** (кодът вече е на десктопа ти,
   `dombi-riders-system.zip` → папка `backend/`):
   ```
   cd backend
   git init
   git add .
   git commit -m "Dombi Riders backend"
   # създай празен repo в github.com (New repository), после:
   git remote add origin https://github.com/<твоя-акаунт>/dombi-riders-backend.git
   git branch -M main
   git push -u origin main
   ```
   После ми кажи URL-а на repo-то (или "готово") и довършвам останалото
   (Render web service, env vars, deploy, проверка) сам.

## 2. Деплой в Render (Free план + Supabase за данните)

Стъпките по-долу изпълнявам аз (през Render connector-а), веднага щом имам
Git repo (виж т. 1):

1. Създавам Web Service в Render — runtime Node, план **Free**, build
   `npm install`, start `npm start`.
2. Задавам `NODE_ENV=production`.
3. **Ти трябва ръчно да добавиш** `DATABASE_URL` като Secret в Render
   Dashboard → Environment (не мога да го направя вместо теб — виж защо в
   бележката по-долу):
   - Отиди в Supabase Dashboard → твоя проект → Project Settings →
     Database → Connection string → избери "URI".
   - Копирай връзката (съдържа паролата на базата) и я постави в Render
     като env var с име `DATABASE_URL`.
   - ⚠️ Не мога да въведа този ключ вместо теб дори и да ми го пратиш в
     чата — това е твоя тайна инфраструктурна credential-ка и трябва да
     влезе директно през Render/Supabase, не през мен, като мярка за
     сигурност.
4. По избор: `ANTHROPIC_API_KEY` / `SIGNNOW_ACCESS_TOKEN` (виж коментарите
   в `render.yaml`) — също ръчно от теб, по същата причина.
5. Deploy. При първо стартиране конзолният лог трябва да покаже:
   `Postgres kv_store беше празна — заредена начална база от data/db.json...`
   — това означава, че реалните данни от бекфила са заредени успешно в
   Supabase. При следващ рестарт/redeploy трябва да видиш вместо това
   `Заредена база от Postgres/Supabase (kv_store)...` — знак, че данните са
   оцелели.
6. Смени демо паролите (`admin123`/`manager123`/`driver123`) веднага след
   първия реален вход — през "Потребители и роли" в системата.

**Ако пропуснеш стъпка 3 (не зададеш `DATABASE_URL`):** системата пак ще
проработи (пада обратно на локалния `data/db.json`), но на Free план в
Render това означава реален риск от загуба на всички нови записи (нови
шофьори, нови седмични заплати, всичко въведено след деплоя) при следващ
redeploy или рестарт на контейнера. Настоятелно препоръчвам стъпка 3.

- [ ] "Досиета на служители" показва всички 70+ профила (реалните шофьори).
- [ ] "Заплати" → избран шофьор показва седмичните записи с правилни суми.

### 2.1 Постоянен диск (Persistent Disk) — снимки на документи + автоматични бекъпи

Системата вече прави **автоматични бекъпи на цялата база данни** (профили,
заплати, кандидатури, коли, договори...) — веднъж на 24 часа, плюс един при
всяко стартиране на сървъра, като пази последните 30 копия (виж
`lib/backup.js` и страницата "Резервни копия" в менюто, само за админ роля).
Снимките на документи (лични карти, книжки, селфита) вече се пазят и в
същата логика.

**Проблем на Render Free план:** дискът е ефимерен — всичко записано на диска
(снимки в `data/uploads/`, бекъпи в `data/backups/`) се губи при всеки
redeploy/рестарт на контейнера. Автоматичните бекъпи по-горе са безполезни
без постоянен диск, защото самите бекъп файлове изчезват заедно с всичко
останало.

**Решение — Render Persistent Disk** (изисква платен план, минимум
Starter, ~$7/мес, плюс самия диск ~$0.25/GB/месец, 1GB е достатъчен за
начало):

1. Ъпгрейдни `dombi-riders-backend` до план Starter (или по-висок) в Render
   Dashboard.
2. Render Dashboard → услугата → Disks → Add Disk. Задай Mount Path, напр.
   `/var/data`.
3. Environment → добави `DATA_DIR` = същия път (`/var/data`).
4. Redeploy. Оттук нататък и снимките (`UPLOADS_DIR`), и бекъпите
   (`BACKUPS_DIR`) автоматично сочат към постоянния диск — не се налага
   никаква друга промяна в кода.

**Важно да се разбира и след диска:** тези бекъпи пазят само базата данни
(профили/заплати/кандидатури и т.н. — точно каквото е в Supabase
`kv_store`). Те НЕ са бекъп на самия Supabase проект — ако Supabase
акаунтът/проектът бъде изтрит или поврежден по друг начин, локалният
JSON бекъп на диска в Render е достатъчен, за да се възстанови всичко
ръчно (виж бутона "Възстанови" в "Резервни копия"), но възстановяването
е ръчно действие, не автоматично. Ако искате и истински Point-in-Time
Restore на самата база (без ръчна стъпка), това се осигурява чрез
Supabase Pro план (вижте прегледа на вариантите с бизнес собственика).

## 4. Текущ Supabase модел vs. бъдеща пълна релационна миграция

**Какво е направено сега:** Supabase Postgres се използва като прост,
надежден key/value склад (таблица `kv_store`, един ред с цялата база в
JSON вид) — виж т. 0. Това реши конкретния проблем (Free план в Render без
диск) с минимална, добре тествана промяна в `lib/db.js`, без да пипа
останалата логика на приложението (317-те payroll записа, 70-те профила и
всичко останало минават през същите функции както винаги).

**Какво НЕ е направено:** `schema.sql` в основната папка е пълна,
релационна Postgres схема (отделни таблици, foreign keys, RLS политики по
роля) — тя НЕ се използва в момента. Прилагането ѝ реално (вместо kv_store
подхода) означава пренаписване на `lib/db.js` функция по функция към SQL
заявки/Supabase клиент — съществена по обем промяна, оставена нарочно за
отделна, по-внимателна сесия, за да не се рискува чупене на системата с
реални данни в нея точно сега.

Когато решите да го направите:
1. `schema.sql` вече е изпълним as-is в Supabase SQL Editor (или през
   `apply_migration`).
2. Профилите (`profiles`) в схемата очакват `auth.users` запис за всеки
   потребител (Supabase Auth управлява имейл/парола отделно от таблицата
   `profiles`) — ще трябва скрипт, който създава `auth.users` + `profiles`
   ред за всеки от 70-те реални шофьора (през Supabase Admin API, не
   директно в таблицата).
3. `payroll_entries` в схемата вече е разширена с колоните, които реалният
   импорт използва (`platform_breakdown`, `needs_review`,
   `order_count_unknown`, `import_file`, `note`) — вижте коментарите в
   `schema.sql`.
4. Пренапишете `lib/db.js` функция по функция, тествайте всеки маршрут.
5. Изтрийте `kv_store` едва след като новата релационна база е потвърдено
   коректна и синхронизирана.

### 5.3 Направени допускания (проверете ги)
- **Статус "активен"/"спрян":** зададен автоматично — "активен" само ако
  шофьорът има данни в последните 2 налични седмици (03.08–16.08.2026),
  иначе "спрян". Това е евристика по последна активност, не потвърдена
  информация — прегледайте я в "Потребители и роли".
- **Удръжки:** всички исторически записи имат `deduction_amount = 0`,
  защото към онези дати системата още няма реални трудови договори с
  зададена седмична удръжка. Ако в действителност е имало удръжки
  (наем на кола и т.н.) през тези седмици, трябва да ги въведете ръчно.
- **"Платено":** всички исторически записи са маркирани `paid: true`
  (приема се, че вече са изплатени в реалността, тъй като идват от
  финализирани фактури) — коригирайте ръчно, ако не е така за някоя
  седмица.
- **Подписи:** НИТО ЕДИН исторически запис няма подпис
  (`signature_status: 'none'`) — системата никога не измисля подпис на
  шофьор, дори и за минала седмица.

## 6. Как работи текущият (бъдещ) импорт от UI-то

`public/payroll.html` → панел "Импорт от Bolt / Glovo": админ качва .xlsx
файл, системата съпоставя куриерите по телефон със съществуващи профили,
показва преглед (съпоставени / несъпоставени / записи за проверка) и
изисква изрично потвърждение преди запис. Логиката е в
`lib/earnings-import.js`.

⚠️ **Пакетът `xlsx` (SheetJS)**, от който зависи този импорт, е добавен в
`package.json`, но **не можа да бъде инсталиран и тестван в средата, в
която е разработена системата** (без достъп до npm registry там). Кодът
е внимателно преписан от логика, ръчно проверена срещу двата реални
файла (виж т. 5), но **задължително тествайте с реален файл веднага след
първия деплой в Render**, преди да разчитате на този път за реални
седмични импорти — панелът показва ясно съобщение, ако пакетът липсва,
вместо да се държи сякаш работи.

## 7. Пакетирани файлове

Цялото съдържание на тази система (бекенд + маркетинг сайт + този
документ + `schema.sql`) е копирано в папка на работния плот на компютъра
ви (виж съобщението в чата за точното име на папката).
